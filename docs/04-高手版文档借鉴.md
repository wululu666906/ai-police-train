# AI虚拟警情处置模拟训练平台：系统化重构反思与AI协作微调方案

> 版本：v1.0  
> 适用范围：当前仓库（`Vue3 + FastAPI`）  
> 目标：把“可运行的训练系统”升级为“可持续演进的平台型系统”

---


## 2. 结合本项目现状的差距画像

### 2.2 核心差距

- **产品层**：已有功能说明，但“版本边界（P0/P1/P2/不做）”仍不够硬，易边做边扩。
- **前端层**：以 `views` 页面推进为主，页面间信息架构与复用策略尚未形成统一规范。
- **后端层**：`main.py` 兼顾较多兼容逻辑与路由挂载，模块治理规范（版本化、聚合接口、可观测）还可加强。
- **验证层**：后端有测试但偏“存在”，尚未形成“每轮迭代必过”的质量门禁。
- **协作层**：AI 提示词经常描述目标，但对“目录约束、验收命令、未完成项披露”约束还不够强。

   - 如何验证
   - 风险点
   - 未完成项
   - 下一步建议

### 3.2 做前后端“结构收敛”

1. 前端收敛方向（保持 Vue，不盲目切栈）
   - 维持 `views`，但按业务域整理组件与组合逻辑：
     - `components/cases`
     - `components/training`
     - `components/evaluation`
     - `components/shared`
   - 把页面内硬编码数据和复杂流程逐步外移到：
     - `src/composables`（交互逻辑）
     - `src/services`（接口与领域服务）
     - `src/types`（领域类型）
   - 形成“页面负责编排，逻辑在 composables/services”规范。

2. 后端收敛方向（保持 FastAPI，强化模块边界）
   - 逐步引入 `/api/v1` 语义（兼容老接口，避免一次性破坏）。
   - 在 `routers` 现有基础上补“聚合接口”思路，减少前端多请求拼装。
   - 把启动兼容逻辑和业务逻辑继续下沉，减轻 `main.py` 入口负担。
   - 将“配置安全项”显式化（密钥、CORS、默认账号策略、环境校验）。

### 3.3 补“平台级能力”

- 可观测性最小版本：请求日志、错误分类、关键链路耗时。
- 数据质量治理常态化：把清洗脚本能力转为可重复执行流程。
- 评估回归集：对评分稳定性做回归测试，避免版本漂移。

## 4. 执行准则

### 4.1 产品拆解准则（每次新需求先写）

每个需求必须先回答 6 个问题：

1. 给谁用（学员/教官/管理员/领导演示）？
2. 解决哪个“训练环节阻塞”？
3. 第一屏第一眼要看到什么？
4. 本期 P0 必须交付什么？
5. 哪些属于 P1/P2？
6. 本期明确不做什么？

### 4.2 信息架构准则（前端改动前先画）

对于管理端与学员端页面，都先定义：

- 顶部：身份、状态、关键入口
- 中区：主任务区域（本页核心动作）
- 侧区：上下文信息（提示、状态、风险）
- 底区：历史、扩展动作、辅助入口

若不能回答“用户第一眼看什么、第二步点哪里”，则不进入编码。

### 4.3 工程分层准则（编码时强制检查）

- 视图层不塞业务规则。
- 业务规则不直接耦合 UI 组件。
- API 返回结构先定义类型，再落组件。
- 每个新增能力都要有“可回归验证点”。

## 5. 本项目专用 AI 提示词（微调版）

以下模板专门适配当前仓库，不要求切到 React，不要求推倒重写。

### 5.1 重构任务总提示词（项目专用）

你是本项目的产品架构师 + Vue 前端负责人 + FastAPI 后端负责人 + 交付负责人。  
请基于当前仓库进行“增量重构”，禁止推倒重写。

项目背景：
- 项目是 AI 虚拟警情处置模拟训练平台，已有主链路：案件 -> 训练 -> 评估 -> 历史。
- 技术栈固定：前端 Vue3 + TS，后端 FastAPI + SQLAlchemy。

执行要求：
1. 先审计当前代码结构与可复用模块，不要立即写代码。
2. 先输出本次需求的产品拆解（用户、问题、P0/P1/P2、不做项）。
3. 给出文件级改动计划，明确每个文件改动目的。
4. 严格保持目录风格：`frontend/src/views|components|composables|services|types` 与 `backend/routers|services`。
5. 优先做“页面编排与业务逻辑分离”，避免把复杂逻辑继续堆入 `views`。
6. 后端新增能力优先通过模块路由与服务层实现，不把业务逻辑堆进 `main.py`。
7. 完成后必须执行验证命令：
   - `frontend`: `npm run build`
   - `backend`: `python -m pytest`
8. 最终输出必须包含：
   - 改动文件清单
   - 验证结果
   - 已完成项
   - 未完成占位项
   - 风险与下一步建议

### 5.2 页面迭代提示词（项目专用）

请基于当前 Vue 页面做“结构化重构”，不要重做 UI 风格。

要求：
1. 先给页面信息架构（顶部/主区/侧区/底区）。
2. 把页面内复杂逻辑抽到 composables 或 services。
3. 所有接口数据先补 TypeScript 类型定义。
4. 保持现有交互行为不回退。
5. 完成后给出回归检查点（至少 5 条）。

### 5.3 后端优化提示词（项目专用）

请在当前 FastAPI 后端做“模块化增强”，保持现有接口兼容。

要求：
1. 新增或改造接口时优先使用路由模块 + service 层。
2. 对关键接口补 pytest 用例（正常/异常/鉴权）。
3. 配置项通过环境变量管理，不硬编码敏感配置。
4. 明确本次改动的兼容策略（旧路径是否保留、如何迁移）。
5. 输出接口清单、返回结构示例与验证命令。

## 6. 

### 6.1 产品与架构

- 训练“先边界后功能”：每次先写 P0/P1/P2/不做项。
- 训练“页面讲故事能力”：先信息架构，再组件实现。

### 6.2 前端工程化（贴合现栈）

- Vue 组合式 API 分层（`views` vs `composables`）。
- 类型先行（接口类型、领域对象、状态类型）。
- 页面级回归清单编写（避免改一个坏一片）。

### 6.3 后端工程化（贴合现栈）

- FastAPI 路由与服务分层边界。
- 聚合接口设计与接口版本策略。
- pytest 用例覆盖关键业务路径。

### 6.4 AI 协作方法

- 不再只说“做高级点”，而是给角色、目标、范围、约束、验收。
- 每轮都要求 AI 报告“未完成项与风险”，防止假完工。
- 每轮都要求跑验证命令，建立“可证据化交付”习惯。

## 8. 结语（针对本项目）

这个项目现在最需要的不是“再加一批功能”，而是把已有能力沉淀成**稳定、可维护、可演进**的系统资产。  
在本仓库要坚持“增量重构”原则：
- 不推倒现有主链路
- 不盲目换技术栈
- 先收敛边界，再扩展能力

只要持续按“产品边界 -> 信息架构 -> 工程分层 -> 验证闭环”执行，你和高手版之间的差距会快速缩小，而且会更贴合你这个警务训练场景的真实交付节奏。
