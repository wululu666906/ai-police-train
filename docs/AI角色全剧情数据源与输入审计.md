# AI 角色全剧情数据源与输入审计

## 1. 审计结论

角色生成链路改为以案件完整剧情为全局逻辑基准，并以角色专属事实账本限制角色可说范围。单角色和多角色生成统一通过 `role_generation_context_service` 编译上下文，避免两条链路各自维护不同的数据拼装规则。

完整剧情负责核对人物、时间、地点、因果和结果；角色知识账本负责判断当前人物是否亲历、听说、隐瞒或不知道。完整剧情不是角色可直接全部复述的台词素材。

## 2. 全剧情数据源

| 项目 | 规则 |
|---|---|
| 专属命名空间 | `case:{case_id}` |
| 节点 ID | `story` |
| 节点类型 | `complete_story` |
| 主读取来源 | `case_knowledge_nodes` |
| 兼容回退 | `structured_data.complete_story`、`full_narrative`、`story_world.complete_story`、`narrative_document.content` |
| 最低回退 | 案件背景或原始材料 |
| 一致性标识 | SHA-256 内容哈希 |
| 同步时机 | 案件创建、更新、重新生成并执行知识同步时 |
| 每轮角色生成 | 强制读取，不依赖可选 RAG 开关 |

## 3. 十三类输入有效性审计

| 编号 | 原输入类型 | 有效性 | 问题与影响 | 治理结论 |
|---:|---|---|---|---|
| 1 | 角色身份、类型、状态 | 高 | 是身份锚点；缺失会导致串戏 | 保留 |
| 2 | 角色事件记忆 | 高 | 是角色回答的事实依据 | 保留，统一进入角色事实账本 |
| 3 | `knows_facts` 等可说事实 | 中 | 与 `known_information`、`known_key_points` 重复，造成同义内容多次出现 | 合并并去重，不再独立重复输出 |
| 4 | `hidden_truths` 等隐瞒事实 | 高 | 决定披露边界；重复字段会强化模型照抄 | 合并为 `withheld` 模式 |
| 5 | `does_not_know` 等未知事实 | 高 | 防止模型补造 | 合并为 `unknown` 模式 |
| 6 | 场景信息 | 高 | 约束当前空间、在场人物和任务范围 | 保留 |
| 7 | 阶段目标、考察点、动作目录 | 中高 | 对训练推进有效，但不能成为角色事实来源 | 保留，优先级低于剧情和角色事实 |
| 8 | 已公开信息 | 高 | 支持角色根据现场公开内容作答 | 保留并去重 |
| 9 | 对话历史和累计摘要 | 高 | 维持上下文并避免重复 | 保留；短历史与累计摘要职责分离 |
| 10 | 情绪、信任、配合、风险、清晰度 | 高 | 控制行为表现；不应改变客观事实 | 保留为动态状态 |
| 11 | 人设画像、角色剧本、表面口径 | 中低 | 多个描述块语义重叠，容易压过本轮问题或被直接念出台词 | 删除未被提示词消费的重复拼装；运行时只保留最小人物线 |
| 12 | 状态契约和真人化反应 | 高 | 控制本轮长度、语气、披露和状态变化 | 保留；作为行为约束而非事实来源 |
| 13 | RAG 召回 | 低到中 | 案件类召回会引入其他人物或全案知识；法规材料可能使群众角色说话过于专业 | 多角色案件事实链路下线；单角色仅作为可选法规、SOP、教学补充 |

## 4. 已下线或合并的输入

### 4.1 从实际提示词下线

- 独立案发时间、地点、报警时间和裸时间线：已由完整剧情统一覆盖，避免重复和版本冲突。
- 单角色中未被模板使用的角色类型、性格、表面口径、触发点等重复格式化参数。
- 单角色重复的 `persona_block`、角色剧本块和场景模式说明块。
- 多角色中未被当前提示词使用的完整画像块、角色大脑文本块、全案基准占位块。
- 多角色外部 RAG 召回：角色案件事实由全剧情与专属记忆提供，不再执行无效检索。
- 格式化后的“事实账本 + 可说/隐瞒/未知三栏”重复展示：只保留统一账本。

### 4.2 兼容字段合并

| 统一语义 | 兼容来源字段 |
|---|---|
| `known` | `knows_facts`、`known_information`、`known_key_points` |
| `withheld` | `hidden_truths`、`hidden_information`、`withheld_key_points` |
| `unknown` | `does_not_know`、`cannot_answer` |
| `ledger` | `role_event_ledger` 优先，兼容 `knowledge_ledger` |

兼容字段暂不从数据库结构删除，以保证旧案件仍可读取；它们不再作为多套独立接口重复进入模型。

## 5. 新提示词裁决顺序

1. 读取完整剧情，建立全局人物、时间、地点、因果和结果基准。
2. 读取角色专属事实账本，确定本人知道、隐瞒、听说和不知道的范围。
3. 读取学员本轮输入、现场公开信息、当前场景和对话历史。
4. 使用阶段目标判断训练推进，但不得由考察点反向创造案件事实。
5. 使用动态状态和人物线决定语气、长度、犹豫、回避或披露程度。
6. 生成台词后执行事实依据、身份、重复、元话语和状态契约校验。

## 6. 风险控制

- 全剧情直接进入模型会提高全局一致性，也会增加角色越权知情风险，因此提示词明确区分“全局推理基准”和“角色可披露事实”。
- `supporting_knowledge_ids` 仍以角色事实账本为准，不能用完整剧情节点代替角色依据。
- 完整剧情缺失时明确进入受限回退，不允许模型自行补全。
- 每轮保存剧情来源、节点 ID、内容哈希和加载状态，便于定位旧剧情、缺失剧情或同步问题。
- 完整剧情长度会增加模型上下文和调用成本，这是全量接入的直接代价；运行监控应重点观察输入 token、响应时延和上下文上限错误。

## 7. 预期效果

- 提升跨阶段时间线、人物关系和因果一致性。
- 降低只依赖局部记忆导致的答非所问和剧情断裂。
- 减少重复画像、人设说明和多套事实字段造成的推理噪音。
- 保留角色视角差异，避免所有角色输出同一份全案总结。
- 通过内容哈希提高问题追踪和剧情版本核对能力。
